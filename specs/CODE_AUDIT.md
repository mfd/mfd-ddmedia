# Аудит кода медиа-бота — 25 октября 2026

Проверена локальная версия `2026.10.25.02.03`: `bot/main.py`, `media.py`, `metadata_worker.py`, `storage.py`, `links.py`, `url_validation.py` и конфигурация зависимостей. Это статический аудит. В текущем проходе не проводились нагрузочный тест, длительное наблюдение за RSS и проверка новой версии на сервере. Ранее выполненный замер двух минут 4K AV1→H.264 показал пик RSS FFmpeg около 390 MiB; он не доказывает отсутствие утечки при длительной работе.

## Высокий приоритет

1. **Фоновые задачи могут завершиться, пока бот остаётся активным.** `main.py:892–905` вызывает `disk_critical()` и `storage.next_queued()` вне блока обработки ошибок. `main.py:1034–1038` запускает `worker()`, `cleaner()` и `disk_guard()` через `create_task()`, но не наблюдает за их завершением до остановки polling. Исключение SQLite или файловой системы в этих местах оставит процесс Telegram активным, а очередь — без обработчика. Нужны supervisor фоновых задач, сигнал о сбое владельцу и перезапуск процесса при потере обязательного worker.

2. **Ограничение URL не защищает все последующие сетевые запросы.** `url_validation.py:63` разрешает неизвестные домены; `media.py:74–83` проверяет DNS только для исходного адреса и передаёт URL в `yt-dlp`. Переадресации, повторное разрешение DNS и запросы самого экстрактора не проходят ту же проверку. В разрешённой группе ссылку может прислать любой участник (`main.py:312–318`). Это потенциальный SSRF к локальным службам VPS. Нужны проверка каждого фактического назначения и переадресации либо сетевое ограничение отдельного процесса `yt-dlp`; дополнительно стоит ограничить поддерживаемые сайты, если произвольные сайты не требуются.

3. **Отмена и защита свободного места не работают во время перекодирования.** `media.py:221–230` проверяет отмену и свободное место только в progress hook загрузки. Затем `media.py:257–261` запускает блокирующий FFmpeg с тайм-аутом до четырёх часов. Кнопка отмены и `disk_guard()` лишь ставят флаг (`main.py:691–700`, `main.py:939–960`), который FFmpeg не читает. В этот период один worker занят, а готовый файл может заполнить диск. Следует запускать FFmpeg как управляемый дочерний процесс, проверять отмену и место, завершать всю группу процессов и удалять частичный результат.

4. **Предел размера не учитывает все временные файлы.** `main.py:779` передаёт лимит одному вызову загрузки; `media.py:226–229` сравнивает его с `downloaded_bytes` текущего потока. Во время скачивания видео и аудио, объединения и повторной кодировки на диске могут одновременно лежать несколько копий; после начала FFmpeg резерв места не контролируется. Нужна квота на весь каталог задачи и оценка пикового места до запуска объединения/конвертации.

## Средний приоритет

5. **Неограниченные буферы вывода дочерних процессов.** `main.py:84–103` собирает весь JSON метаданных через `communicate()` без лимита размера; `metadata_worker.py:18` сериализует полный ответ. `media.py:257–261` собирает весь вывод FFmpeg через `capture_output=True`, а `media.py:273–282` — stderr через `communicate()`. Большой ответ или поток ошибок может занять существенную часть 2 GB RAM. Нужны пределы размера метаданных и вывода, ограниченный хвост stderr и лимит памяти дочернего процесса. При тайм-ауте метаданных `main.py:90–93` убивает только Python-процесс; запущенные им помощники, например JavaScript runtime `yt-dlp`, могут остаться. Нужна отдельная группа процессов с групповым завершением.

6. **SQLite растёт без очистки, включая сообщения без авторизации.** `main.py:106–117` пишет сообщение до проверки доступа; `storage.py:123–128` сохраняет до 2000 символов каждого сообщения. `storage.py:72–85` постоянно добавляет карточки и задания, а `storage.py:142–150` лишь обнуляет ссылки на удалённые файлы. Срок хранения и удаление старых записей не заданы. Это рост диска и риск хранения чувствительных ссылок; регулярные `commit()` на потоке событий также могут замедлять ответы. Нужны ограничение записи, срок хранения и очистка старых `message_log`/`jobs` с контролем WAL.

7. **После аварии остаются частичные медиафайлы.** `storage.py:115–121` помечает прерванные задания как `failed`, но не очищает каталоги. `main.py:923–936` удаляет только записи с `file_path` и истёкшим `delete_after`. Файлы, не успевшие попасть в базу, могут накапливаться после перезапусков. Нужна сверка каталога `DATA_DIR/jobs` с БД при старте и безопасная очистка старых осиротевших задач.

8. **Есть две небольшие реальные утечки состояния Python.** `main.py:332–336` добавляет запись в `last_progress` для каждого задания и нигде не удаляет её. `main.py:695–699` добавляет ID отменённой задачи из очереди в `cancelled_jobs`, но worker больше не выбирает эту задачу, поэтому `main.py:919` её не удалит. Рост медленный, но неограниченный. Удалять оба ключа при любом финальном статусе, включая отмену до запуска.

9. **Последовательность обеспечена только одним запущенным экземпляром.** `main.py:1034` создаёт один worker, а `main.py:77–79` и `main.py:777–780` защищают метаданные и загрузку одним `asyncio.Lock`. Однако `storage.py:106–107` выбирает очередную строку без атомарного захвата между процессами. Два экземпляра бота способны взять одну задачу и запустить два скачивания. Требуется блокировка на уровне БД или гарантия одного экземпляра на уровне запуска.

## Низкий приоритет

10. **Временная ссылка для варианта «лучшее качество» может возвращать 404.** `links.py:22–26` формирует имя с `bestp`, а регулярное выражение в `links.py:39` принимает только числовое разрешение `\d+p`, `m4a` или `mp3`. Нужно согласовать генератор и проверку имени.

## Вывод по памяти

Большие кадры FFmpeg живут в отдельном дочернем процессе и освобождаются при его завершении; в коде не обнаружено сохранения самих кадров в Python. Реальные источники роста — неограниченные stdout/stderr и метаданные, долгоживущие записи в БД, два словаря состояния и потенциально оставшиеся после тайм-аута дочерние процессы. Один успешный замер RSS не заменяет наблюдения памяти в течение суток под обычной нагрузкой.
